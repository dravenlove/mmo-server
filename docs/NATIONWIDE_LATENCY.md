# 全国玩家连接延迟：部署选择与测量

## 当前两机方案能改善什么

游戏主机承载 Gateway、Game Backend 和 C++ 场景，移动、技能和视图不再等待跨地域的场景调用。鉴权后台仅参与注册和登录，不能把玩家每次操作经由鉴权机再转发到游戏主机。外部 MySQL仍是会话、快照、经济等操作的依赖；优先让数据库靠近游戏主机。

这能消除原架构的内部跨地域等待，无法消除全国各地玩家到同一机房的距离、运营商互通、丢包与抖动。两个机器不能同时实现全国就近的权威场景。不要只根据公网 ping 判断角色是否跟手，也不能承诺全国固定几十毫秒。

## 按投入逐步选择

| 阶段 | 做法 | 能改善 | 限制与成本 |
| --- | --- | --- | --- |
| 当前两台 | 实时服务同机；客户端直接连游戏入口；Auth 走加密控制链路 | 移除游戏内部跨地域往返 | 玩家仍连接同一机房；SSH只用于内部鉴权/数据库，不给全国玩家绕路 |
| 单区线路优化 | 按真实玩家分布测试多线 BGP、地域和公网带宽 | 改善部分运营商路径、丢包和带宽瓶颈 | 换地域涉及迁移；BGP/带宽不能缩短物理距离 |
| 多地加速入口 | 评估腾讯云 GAAP TCP 监听器；玩家连接加速域名，源站仍是当前游戏入口 | 就近接入，并通过加速网络回源，可能减少绕路与抖动 | 额外收费；回源距离仍在；需对照测试，有些线路提升有限 |
| 多个游戏区域 | 华北、华东、华南等地区各有 Gateway+场景集群，登录后按玩家/队伍选择区服 | 权威模拟靠近玩家 | 需要更多主机、路由能力、跨区数据设计；同一场战斗仍应在一个权威区域 |

GAAP 的能力和 TCP 配置以 [腾讯云产品说明](https://cloud.tencent.com/document/product/608/13759)与 [TCP/UDP 监听器文档](https://cloud.tencent.com/document/product/608/118426)为准。这里仅提出可评估方案，未创建付费实例，也未验证当前游戏通过加速后的体验。不应预填一个节省比例或固定时延。

普通网页 CDN 不能直接加速本项目的任意 TCP 长连接。仅把 Gateway 放到玩家附近、场景仍在远方，会把距离移动到 Gateway→Scene；可能借助更好骨干线路获益，但不等于权威结算就在本地。

## 先测再决定

建议先从华北、华东、华南、西南/西北各找至少一个测点，并覆盖主要运营商。使用相同客户端、同一版本、相似时间段和持续操作路线，分别记录：

| 指标 | 用途 |
| --- | --- |
| 未登录网关 ping RTT 的 P50/P95/P99 | 入口往返与基础抖动 |
| 已登录连接的移动回执、技能回执与错误率 | 实际业务等待，包含调度和服务调用 |
| 实际状态到达间隔和长间隔次数 | 判断推送积压、断流和网络不稳定 |
| 同机 Gateway→Scene 完整视图耗时 | 确认内部链路优化生效，不能只读小健康响应 |
| 丢包、重传、出口带宽、CPU与内存 | 区分线路与资源瓶颈 |
| 按键到首个对应显示帧 | 最终操作体验，包含客户端显示处理 |

分别比较直连与加速入口，保留高峰/非高峰数据。判断依据应是各地区实际业务尾延迟与错误率，不只看平均 ping。先建立本项目基线，再设验收阈值；本文件没有把建议当作全国实测结论。

## 客户端现状与后续边界

本轮不修改客户端。现有约 5Hz 的名义状态推送、显示插值和缺少本地移动预测仍可能让按键反馈慢于网络 RTT。把服务移到同机后，这些等待不会自动消失。

以后若要进一步提高跟手感，按 [客户端响应需求](CLIENT_RESPONSIVENESS_REQUIREMENTS.md)明确输入确认、预测和服务端校正后另行开发。预测能改善自己的即时显示，命中、伤害和场景归属仍由权威服务器决定；不能把视觉反馈时间宣称为服务器结算延迟。

在现有预算下，先采用单游戏区与独立鉴权后台，收集真实玩家测量，再决定是否需要付费加速。只有玩家分布和规模证明单区无法满足目标时，再扩展多个游戏区。
